# Adding translations and formatting values

SFT-26 (K-7) learning guide. Reuse the existing helpers; no new i18n library is needed.

## Where the locale comes from

`apps/web/proxy.ts` keeps explicit `/ar/...` and `/en/...` paths, regardless of browser language. A path without a locale redirects to Arabic, preserving its path and query string. `app/[locale]/layout.tsx` awaits `params`, validates the locale, and sets `<html lang="ar" dir="rtl">` or `<html lang="en" dir="ltr">`. Its metadata and the home page select translations on the server with `getTranslator(locale)`.

The URL chooses the catalogue; there is no automatic English message fallback. Unknown nested paths currently render the translated 404 page, rather than a new feature page. See [Next.js internationalisation](https://nextjs.org/docs/app/guides/internationalization) for the route-segment approach.

## Add a string in both languages

1. Add the same key under the same object in `apps/web/messages/ar.json` and `en.json`. This PR adds `common.lastUpdated` as a learning example; it does not add UI:

   ```json
   { "lastUpdated": "آخر تحديث: {date}" }
   ```

   ```json
   { "lastUpdated": "Last updated: {date}" }
   ```

2. In a server component, validate the route locale and translate it:

   ```tsx
   import { notFound } from "next/navigation";
   import { getTranslator, isLocale } from "@/lib/i18n";
   import { formatDate } from "@/lib/format";

   export default async function Example({ params }: { params: Promise<{ locale: string }> }) {
     const { locale } = await params;
     if (!isLocale(locale)) notFound();
     const t = getTranslator(locale);
     const date = formatDate("2026-10-03T09:00:00Z", locale);
     return <p>{t("common.lastUpdated", { date })}</p>;
   }
   ```

   Arabic gives `آخر تحديث: 3 أكتوبر 2026`; English gives `Last updated: October 3, 2026`.

3. Run the tests below. Arabic defines the key types; English must match. Catalogue tests check matching keys, nonempty strings and matching placeholders. Unknown keys throw instead of falling back; missing placeholder values remain visible as `{date}`. Pass translated strings as props to client components so both catalogues stay out of the browser bundle. Client components needing just locale helpers should import `@/lib/locale`.

## Format an amount, percentage and date

Use `apps/web/lib/format.ts`, which wraps `Intl.NumberFormat` and `Intl.DateTimeFormat`. The helpers explicitly preserve Western digits (0–9), Gregorian dates and Saudi time (`Asia/Riyadh`). Both languages can therefore produce the same number; that is intentional.

```tsx
import { Riyal } from "@/components/Riyal";
import { formatDate, formatNumber, formatSAR } from "@/lib/format";

// In a component with a validated locale:
const amount = formatSAR(1500, locale); // "1,500" in both locales
const percentage = formatNumber(0.155, locale, {
  style: "percent",
  maximumFractionDigits: 1,
}); // ar: "15.5٪" (or "15.5%", depending on ICU); en: "15.5%"
// Percent input is a fraction (0.155), not 15.5.
const date = formatDate("2026-10-03T09:00:00Z", locale);
// ar: "3 أكتوبر 2026"; en: "October 3, 2026"

// For a visible SAR amount, use the existing symbol component:
const amountView = <Riyal value={1500} locale={locale} />;
```

`Riyal` adds the official symbol, a translated accessible currency label and LTR isolation for RTL text. `formatSAR` returns only the number. Use these helpers instead of bare `toLocaleString()` or new formatters in application code. See [Intl.NumberFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat).

## Verify the examples

```bash
pnpm --filter web exec vitest run lib/i18n-learning.test.tsx lib/i18n.test.ts lib/format.test.ts
pnpm check
```

`i18n-learning.test.tsx` executes the existing proxy, async server layout/metadata and catalogue page for both locales, verifies URL precedence over browser language, checks the new translation and missing-key behavior, and renders the SAR example. It mocks the build-time font module, database reads (an empty catalogue) and client language switch. These are component/unit checks, not a running Next.js HTTP test.

To verify actual routes, run `pnpm --filter web dev`. Open `/ar/missing-page` and `/en/missing-page`: each should return a 404 with locale-specific site metadata. Open `/missing-page?q=card` to check its redirect to `/ar/missing-page?q=card`. With the database configured and seeded (see [deployment setup](deploy.md)), also open `/ar` and `/en` to check the catalogue. For visual changes, check Arabic at phone width using [the RTL guide](rtl.md).

Local production-server checks for this task confirmed locale-specific metadata on both nested 404 routes. An existing limitation in Next.js 16.4.2's error response was observed: the initial document uses `<html id="__next_error__">`, while the locale layout's `lang`/`dir` and translated 404 copy appear in the React payload. Do not treat a payload match as proof of correct initial HTML attributes or a visual RTL check. Full catalogue HTTP checks require `DATABASE_URL`; without it both home pages return 500. This learning change leaves those application/environment concerns untouched.
